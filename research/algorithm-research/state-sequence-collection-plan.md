# 状态序列预测与采集修复方案

状态：原始审计与设计依据。此次实现状态覆盖、首次空快照、单来源失败/恢复、后台窗口校验、实际文档自动识别、层级样本、补全标签分离及旧数据可恢复迁移。推荐算法、候选策略、Safari 和新的应用内部子页面适配不属于本次实现；用户确认暂不需要新增适配。下文“当前代码确认的问题”是修复前审计，不代表修复后的行为，最终契约见 [DATASET](../../docs/DATASET.md)。

## 1. 模型判断

用“截至当前的前台、后台和行为序列”预测下一次目的地变化，符合项目需要。推荐形式为：

`P(下一目的地、等待时间 | 截至 t 可用的状态观测、历史变化、各来源覆盖情况)`

这里的状态是系统已经观察到的信息，不是假定完整、同时取得的真实桌面。应用、窗口、页面和目录/文件保留类型与层级关系；一次到达可以同时有多个层级标签，不拆成互相竞争的三次访问。是否启动应用、抬起窗口、激活标签页或重开地址，由执行时仍有效的入口决定。

必须明确以下边界：

1. **观测范围。** 每个来源有能力、成功/失败、观测时间和覆盖范围；后台数据是模型输入的一部分。缺失与空集合不同。快照数量不能证明覆盖完整。
2. **预测时点。** 输入只使用在截点之前已经可用的信息；跨来源轮询不等于原子快照。保留采集开始、结果接收/可用时间、来源顺序和会话顺序，不能仅按回填的观测时间排序。
3. **到达、补全与意图。** 初次显露、后续真实导航及异步补全可以关联，但不能把补全自动计作下一次行为，也不能把后来的具体页面倒填成较早预测时点的输入。稳定停留是证据，不是已确认最终意图。
4. **类别与实例。** 同一网址或文件可由多个实时窗口入口承载；会话 ID 变化不创造新的长期语义目标。但两个同属一个应用的不同文档仍可能是不同目的地。没有可靠定位符时只能保留应用/窗口粒度，不能编造跨会话对应关系。
5. **时间与候选范围。** 保留停留时间、事件间隔及观察中断；完整观察下无变化与没有观察不同。推荐候选包括当前入口和过去观察过、现在仍可重开的目标，不能只限于后台已打开集合。首次出现的未知网址/文件不能保证事先精确推荐。

“语义相近”需要通过共享的应用归属、窗口关系、URL/路径层级等特征或模型结构表达，不会仅因放入同一序列自动成立。先验证转移与近期访问基线，再决定更复杂的模型。

## 2. 当前代码确认的问题

| 问题 | 当前证据 | 对状态序列的影响 |
| --- | --- | --- |
| 前台事件早于初始库存 | `RecorderModel.start()` 先 `activate()`，后 `scanApplications()`；浏览器/Finder/QSpace 异步补全 | 合法到达可能尚无后台输入，不能自动标为完整状态 |
| 来源失败清空全部库存 | 浏览器断连调用 `gap()`；该方法清空所有来源；`NavigationSampleBuilder` 遇到缺口同样清空 | 健康来源也失去连续引用，恢复前又可出现新前台锚点 |
| 首次空快照被忽略 | `setInventory()` 对没有旧状态的普通空列表直接返回 | 无法区分已成功观察为空和从未观察 |
| 失败被表达为空 | Finder/QSpace 读取失败调用 `setInventory(source, [])`；前台 AX 失败也可能形成空入口更新 | 训练若只读入口集合，会误读为空；现有状态事件仍需联合解释 |
| 缺少逐来源的样本完整性契约 | `NavigationSample` 只有库存引用和后续观察窗口状态；没有预期来源清单及逐来源覆盖 | `observed_horizon` 不等于输入状态完整 |
| 后台普通窗口更新滞后 | 0.5 秒 tick，每 4 次只扫描一个后台应用 | N 个后台应用一轮约需 2N 秒，失败或调度还会增加延迟；旧快照不能直接称为实时状态 |
| 文件自动识别受登记限制 | `observeFront()` / `scanBackgroundWindow()` 仅将 AXDocument 匹配到 `registeredTargets` | 未登记文档通常只留下窗口，无法获得具体文件目的地 |
| 补全仍进入结果序列 | `NavigationSampleBuilder` 先把 context 追加为 outcome，再排除 `resolution_update` 新锚点 | 训练若直接取第一个 outcome，会把观测补全学成下一行为 |

参考实现：[RecorderModel](../../Sources/SmartApp/RecorderModel.swift)、[ContextData / NavigationSampleBuilder](../../Sources/IntentCore/ContextData.swift)、[ContextMonitor](../../Sources/SmartApp/ContextMonitor.swift)。

## 3. 修复状态正确性

### 3.1 每个来源单独描述覆盖

建议每个来源至少保存：

- `sourceKey` 与来源会话/代次：区分应用重启、扩展个人资料连接及重连，防止旧回调覆盖新状态。
- `capability` / `scope`：能观察什么，例如普通浏览器标签页、文件管理器可见窗格、某个应用的标准窗口。
- `status`：`initializing`、`ready`、`unavailable`、`stale`、`not_applicable`；状态转换同时保留原因。
- `snapshotEventID`、`observedAt`、`availableAt`、`lastSuccessfulObservationAt`、最近成功校验/连通性证据。
- `entries`：只有 `ready + []` 才表示该来源在其范围内成功观察为空。被排除对象仍遵守现有无身份边界要求。

快照按变化保存，同时让未变化但重新成功观察的事实可被还原，例如轻量的来源校验事件或检查点；不能把“状态很久未变”和“来源很久没更新”混为一谈。事件驱动与轮询来源需要不同的新鲜度规则。

来源清单来自当时运行的合格应用、启用适配器与实际连接实例；已知不运行可以记不适用，正在运行但扩展未连不能当不适用。不能仅枚举已经成功回报的来源，否则永远未连上的来源不会出现在缺失报告里。

### 3.2 启动、重连和失效

启动先建立来源清单并发起同步，真实前台变化照常保存，同时标记当前同步进度。只在要求的来源达到覆盖条件后生成标为“覆盖达标”的预测输入；超时则降级并明确缺失来源，不无限等待，也不丢掉真实行为。

新快照只能从其结果可用时开始参与在线预测和训练。可以在同步完成时产生新的可用状态记录，但不能用它把较早的样本偷偷补成完整状态。

将单来源故障与全局观察边界分开：浏览器扩展断连一般只使对应来源失效，保留其他健康来源及其时间；休眠、隐私/排除边界及无法确定影响范围的故障继续切断全局关联。来源局部故障不等于所有训练标签都可信：若缺失来源可能承载下一次前台变化，相关标签仍须标为覆盖不足。

后台窗口优先使用受支持的窗口/焦点通知触发刷新，并保留周期校验。Apple 的 [AXObserverAddNotification](https://developer.apple.com/documentation/applicationservices/1462089-axobserveraddnotification) 允许应用对象订阅通知，也明确可能返回“不支持通知”或读取失败；因此需要记录能力并保留轮询回退，不能承诺所有应用均为无损事件流。

### 3.3 可还原且不泄漏未来的状态引用

建议增加可版本化的状态清单，引用当时的前台事件、逐来源库存、来源状态与覆盖结果。所有引用先入库并通过统一校验，再对外发布清单；这保证存储引用一致，不声称不同应用的观测在物理上同时发生。

序列样本分别保存：

- `inputCoverage`：在截点是否满足本次模型所需来源，哪些部分缺失/过期。
- `outcomeCoverage`：后续预测窗口是否持续可观察，是否跨中断或导出尾部。
- `cutoffSequence` / `cutoffAvailableAt`：每份输入必须通过先于截点的检查。
- 到达及补全关联：有证据关联才合并；保留原始事件和补全可用时间。关联不确定时明确标记。

推荐模型可以使用带缺失掩码的样本；要求完整状态的实验则筛掉覆盖不足的输入。两种情况都不能默默将缺失集合补为 `[]`。

## 4. 需要覆盖的目标与关系

以下“覆盖”均受已确认的采集范围与统一准入规则限制。

| 对象 | 要保存的目标/关系 | 当前状态与建议 |
| --- | --- | --- |
| 应用 | 应用身份、运行/退出、前台归属、观察能力 | 已有基础；补齐来源清单与启动/恢复一致性 |
| 工作窗口 | 所属应用、实时实例、焦点/可见/最小化（可观察时）、所承载子目标 | 已采实例；补齐状态、通知/轮询校验和关系一致性；语义类别须有证据 |
| 浏览器网页 | 完整 URL、窗口和标签页归属、选中标签、浏览器是否前台、后台集合 | Chrome/Edge/Brave 有适配代码；每个实际浏览器/个人资料仍需验证。Safari、应用内嵌网页不能默认认为已覆盖 |
| Finder / QSpace 目录 | 完整目录 URL、窗口/可见窗格归属、前台活动项 | 已有；修复失败状态与恢复同步，Finder 继续按稳定停留保留，允许省略中间导航；不扩展到隐藏标签页或目录内容枚举 |
| 已实际打开的普通文件 | 可验证的文件 URL、所属应用/窗口、实时入口与重新打开方式 | 目前依赖手动登记。建议新增“实际工作窗口报告的文档 URL”准入类型，验证后自动收集；不扫描磁盘、选择项或正文 |
| 应用内部子页面 | 应用公开的可重开链接/对象定位符、容器关系 | 按应用逐个适配；无可靠接口时保留应用/窗口粒度，标明未解析，不能只凭标题编造目标 |
| 过去访问、当前已关闭的目标 | 原定位符、历史关系与当前重开能力 | 作为持久目标保留，当前入口状态和历史目标身份分开；不因为不在后台就从候选中消失 |

采集“所有需要的目标”应落实为可检查的覆盖清单：支持什么、实际成功观察什么、缺失什么。首次尚未观察的具体目标没有可靠数据可供提前还原或保证推荐。

## 5. 实施顺序与验收

1. **状态含义与覆盖门槛。** 修复首次空快照、失败状态及逐来源覆盖，保留启动/恢复阶段真实观测；版本化新协议与样本契约。
2. **状态刷新与关系。** 单来源失效、初始同步、过期检测、关闭/重开、跨来源顺序、补全关联和实时入口失效处理。
3. **目标覆盖。** 在统一准入下补实际文档自动识别；按实际使用范围增加 Safari/应用内子目标适配。未经实现及端到端验证的能力不标为完整覆盖。
4. **旧数据派生与基线。** 保留现有原始库/导出，建立新的私有训练 run，重新回放库存和边界；缺失部分保持未知。按时间划分比较近期访问、转移及状态条件化基线，报告层级命中率与候选覆盖率。

关键验收场景：

- 启动时已有多个后台目标，前台变化先到、快照后到：前者明确为同步未完成，后者不能回填过去。
- 成功观察到空集合、尚未观察、权限拒绝、断连四种情况能分别还原。
- 浏览器断连而其他来源正常：只将相关来源标失效；涉及未知前台行为的标签仍判覆盖不足。
- 来源恢复、应用重启、旧异步回调迟到、事件重复/乱序：不污染新代次状态，不重复计算行为。
- 页面在后台加载/刷新：更新状态，不增加前台到达；切回页面时保留应用、窗口、标签页和 URL 关系。
- 同一文档重开产生新窗口：保留不同入口、共享已确认文档身份；同一应用的两个不同文档保持可区分。
- 文件未经手动登记但实际显露：只有得到可验证的文档定位符且通过新准入规则才成为文件目标。
- 每个训练输入引用均已在截点前可用；首个 `resolution_update` 不被直接当成下一行为。
- 报告输入覆盖、后续标签覆盖、各来源缺失原因与持续时间、候选外目标比例及重复/无效引用，不以“总事件多”替代质量验收。

验收需要合成时序测试、导出回放检查及受控的真实应用操作；仅通过编译或单元测试不足以确认目标覆盖。
